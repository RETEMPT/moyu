# 多设备互通与功能取舍

更新：2026-10-06。本页描述 v1.0.0 之后的候选改进，不修改已发布的 v1.0.0 范围。附近传递的服务回归和编译不能替代手机、Pad 真机互通。

## 最有价值的下一步

以“Pad 研读课程资料 → 手机课间回忆自测 → 回到原文核对”为主线。保持现有五项底栏及共享 SVG 图标；学习入口继续放在首页、资料与阅读器，不再增加同等层级的工具页。

商业价值应先证明学生会持续使用、确实节省查找/校对时间，再讨论收费。附近互通本身不证明付费意愿。按照现有价值评估方案，邀请 6～10 名学生试用一周，记录跨端资料传递成功率、查证原文耗时、自测完成率、再次使用及付费意愿；目前没有这批试用结果，不填写虚构分数、收入或效率提升。

手机优先快速查找、拍照校对、自测与待办；Pad 优先长文阅读、笔迹和并排资料。按窗口宽度响应布局，覆盖折叠、多窗口、大字体和软键盘；不要只按设备类型锁死排版。动画应避免与重型解析/文件读写同时争夺主线程；旧 `animateTo` 的弃用告警与性能预算仍需逐页迁移及实际测量。

## 本轮附近传递

使用 `@kit.DistributedServiceKit` 的可信可用设备列表，以及 `@kit.ArkData` 的分布式 KV 手动同步；不接入团队帐号、云盘或远程 AI 服务。

操作：两端安装同一签名身份的候选版本 → 同一华为帐号、系统可信连接并满足组网条件 → 两端打开“外观与数据 → 备份与附近传递”并主动连接 → 发送端选择课程与目标设备 → 在接收端选择发送设备、填写传递码 → 核对资料/题卡/附件数量 → 确认导入为副本。保持发送页面打开，关闭会清理临时条目。

- 只向所选设备及本次传递的键前缀发起同步。临时库 `encrypt: true`、`backup: false`、`autoSync: false`、S2 安全级别；权限拒绝/系统能力缺失时可继续使用文件备份。
- 传递包复用学习备份白名单：正文、PDF、封面、笔迹、已校对页面文字与题卡。缺少真实 PDF 或附件读取失败会拒绝传递，不悄悄丢弃附件。随包示例仍保留示例标记。
- 分片、清单版本、数量/长度和 SHA-256 校验全部通过后才允许导入。UTF-16 分片边界使用 JSON 转义保留中文/表情。单包最多 8 Mi 个 UTF-16 字符，分片最多 32 Ki 字符；这是字符数限制，UTF-8 字节数可能更大，附件编码也有开销。超限改用按课程的文件备份（32 MB 文件、单附件 16 MB）。
- 等待 `syncComplete` 中目标设备的成功结果；45 秒超时、失败或页面关闭均不宣称完成。失败连接不复用，需要重新连接，防止延迟回调被当成下一次成功。
- 传递码 15 分钟有效。正常关闭清理临时条目，异常退出残留在下一次连接清理；已导入副本保留。重复导入同一个包按稳定 ID 跳过已导入资料，并可补齐未成功保存的题卡。
- 保留本地原资料，不合并远端更改，不传播删除。日历/待办、回收站、会话和 Key 不包含在传递中。发起操作成功与对端确认导入成功是不同状态，界面分别提示。

这是一项手动的课程资料传递能力。它尚不是全库连续双向同步，不保证系统连接在离线、休眠、不同帐号/版本或安全等级不兼容时可用。

## 真正双向同步的设计边界

后续使用独立同步仓储，不把本地整库 JSON 作为一个 KV 值自动覆盖。每条业务记录需要稳定 ID、来源设备、操作 ID、版本向量/基础版本、内容摘要和删除记录；时间戳只用于展示，不能单凭设备时钟决定覆盖用户正文。

同一基础版本的单端修改可应用；两端分别修改同一正文时保留双方版本并提示选择，不以最后写入丢弃其中一方。删除记录要阻止旧设备重新带回已删除资料，且需有回收/撤销与记录保留策略。阅读位置、收藏等轻量状态可单独处理；题卡每次复习作为事件记录，避免两端计数互相覆盖。

PDF/自定义封面按内容摘要管理附件，原文件路径仅属于本设备。正文元数据要等附件下载、长度与摘要核验、落盘成功后才发布到界面。断线可重试，不依赖永久网络 ID；启动、后台切换和升级都需恢复任务状态。模型 Key 与第三方鉴权配置保持各端独立。

自动同步默认关闭，只在明确解释范围并授权后开启。不要把 `autoSync: true` 当作任意场景持续同步：官方文档限定其适用的多端协同场景。第一版附近传递的成功数据应先证明值得投入以上同步复杂度。

## 手机与 Pad 是否分别发行

当前不需要。工程只有一个 entry HAP，`deviceTypes` 为 `phone`、`tablet`、`2in1`，同一个 `com.retempt.flowmind` 和版本号，UI 通过响应式规则适配。统一 GitHub 标签、Release、更新说明和签名身份，让两端安装相同候选版本。

正式市场分发提交有效签名的 APP/AppPack，按实际设备部署；GitHub 可提供含 APP/HAP 的 ZIP 与校验信息，手机/Pad 的截图及验收结果分别附上。`arm64-v8a`、`x86_64` 是 ABI，不对应“手机版/Pad 版”；不要据此命名两个端的包。

只有设备专用模块、不同最低系统/能力、独立应用身份或明显不同的更新周期才考虑多产物。即便后续 APP 内包含不同 HAP，也优先统一应用版本和 Release，在说明中写清各产物用途。独立应用身份会额外影响互通与升级路径，不能只为排版差异拆成两个应用。
